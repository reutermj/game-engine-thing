# Retrospective: pong, the first game (2026-09-23)

The first real use of the engine: pong as three mods, played by an agent
(Claude) through a text interface, turn by turn. The goal was evidence about
the design, above all about the bootstrap mod.

What was built: `pong` (components and rules), `pong_ai` (the right paddle)
and `pong_text` (commands and drawing, over messages); a `clock` mod whose
`Clock` component bootstraps publish; a `lockstep` bootstrap that runs frames
only when sent `step N`; and messages to mods (`modctl send <mod> <text>`).

## The game as played

One rally, from the log of play: the agent read `state`, projected the ball's
intercept (wall bounces included), moved the paddle for the computed number
of frames and stepped to contact. It returned all four balls that reached it
and won the point by hitting off-center, putting spin on the ball the AI
couldn't track. Each exchange took three or four tool calls.

Then, mid-game: a per-mod reload made the AI tougher (score and ball kept);
adding a field to `Ball` was refused per-mod, naming the stranded `pong_ai`
and `pong_text` and `//pong:reload`; the game reload swapped exactly those
three, migrated the ball (`added rally (default)`), and play continued.

## What held up

- **Splitting a game into mods was natural.** Rules, AI and interface are
  separate concerns, and the AI and interface only know `pong`'s interface.
  Nothing wanted to cross those lines.
- **The reload model held under real edits.** Implementation changes reload
  per mod in about a second; interface changes go through the game reload,
  which touched only the affected mods. Neither lost game state.
- **Bazel is a safety net for the running game.** Twice an edit that added a
  field broke a struct literal elsewhere; the build failed and the engine was
  never touched.
- **World-keyed setup.** `pong` sets up the court if there's no ball, rather
  than tracking "did I spawn" in its state. That makes it correct after a
  reload, a state reset, or a second copy of the mod, with no bookkeeping. It
  looks like the pattern to recommend.
- **Lockstep time made the game testable.** The same inputs replay the same
  game, so `//pong:pong_test` plays scripted points against the real mods
  and asserts on the result.

## The bootstrap mod

Making the bootstrap a mod paid off once: an agent-playable game needed
different time, and a new bootstrap (about 60 lines) swapped in per game
without touching the loader. But the swap exposed that the bootstrap owns
three separate things:

1. **Time policy:** real-time pacing, or frames on request.
2. **Publishing time:** writing the `Clock`.
3. **Scheduling:** `step_mods`, which runs every other mod in load order.

Only the first needed to change for pong, and the whole bootstrap had to be
rewritten to change it. The consequences:

- **No standard way to control time.** `step N` exists only in `lockstep`.
  Anything else that wants to pause, step, slow down or replay (a debugger, a
  test harness, a "slow motion" key) has to know which bootstrap is loaded.
- **Scheduling is implicit.** Systems run in load order, which is dependency
  order. `pong_ai` runs after `pong`'s physics, so it reacts a frame late, and
  there is no way to say "input, then AI, then physics". A bootstrap can't
  reorder either: `step_mods` is all or nothing. *(Addressed 2026-09-23:
  mods declare systems in phases; pong's schedule is now `input: pong::steer`,
  `update: pong_ai::think`, `simulate: pong::play`. See
  [scheduling.md](../architecture/scheduling.md).)*
- **The loader's loop assumes a busy bootstrap.** It calls the bootstrap's
  step continuously, so `lockstep`, which has nothing to do between requests,
  sleeps 2 ms per call to avoid spinning a core. *(Addressed 2026-09-23: the
  loader has no loop now; a resident bootstrap runs the session and pumps the
  loader, and `lockstep` blocks in the pump. See
  [overview.md](../architecture/overview.md#who-runs-the-loop).)*
- **Input bypasses the frame.** `pong_text` sets the paddle's intent inside
  the message handler, between frames. Harmless for pong; in general, input
  wants to be applied at a defined point in the frame, which is the
  scheduling question again. *(Addressed 2026-09-23: `pong_text` sends a
  `pong::Steer` event, which `pong::steer` applies in the `input` phase.)*

Options, not decided:

- **Split the bootstrap.** Scheduling moves into the loader (or a scheduler
  mod) with explicit phases or ordering; time becomes a swappable source
  (real time, manual) behind one control interface. The bootstrap shrinks to
  a policy, or disappears.
- **Keep the bootstrap, standardize its edges.** Define a time-control
  message protocol (`pause`, `step N`, `rate`) every bootstrap implements, and
  a host service for stepping mods by phase or by name so a bootstrap can
  schedule.
- **Keep it as is** until a second game needs more than load order.

## Other friction

- **No singletons.** `Clock` and `Score` are one entity with one component,
  found with `query().next()`. The writer has to remember its entity, and a
  reader can't tell if there are two. A resource concept (one value per
  component, no entity) would fit both.
- **One query at a time.** A query borrows the world mutably, so `pong`
  copies the paddles out, then moves the ball, then writes back, and
  `pong_text` snapshots everything before drawing. Fine at this size; it will
  hurt as systems touch more components.
- **A new field breaks every literal.** Adding `Ball::rally` broke `Ball {..}`
  in `pong`'s serve. Bazel catches it, but it makes interface changes noisier
  than the migration machinery suggests; `..Default::default()` in literals
  of shared components would help.
- **Text replies are prose.** `state` is readable, but a test (and an agent)
  has to pick numbers out of words. A structured reply would serve both.
- **Round trips.** Each move is an intent message plus a step, and each
  exchange took three or four tool calls. An agent-facing interface could
  offer "step until the ball reaches my side" or report events (`hit`,
  `scored`) instead of making the player poll.
- **Reload reports are noisy.** A game reload lists every unchanged mod; the
  one or two that reloaded get lost in them.
